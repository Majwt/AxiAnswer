# ScriptVault guide

Generated by ScriptVault 0.5.0. `sv init` writes it to `.sv/GUIDE.md`, and
`sv guide` refreshes it whenever sv is newer than the version stamped above
(`sv guide --force` rewrites it either way). Everything below is defined in
`.sv/vault.toml` and `.sv/scripts/`.

## Installation

Install the `sv` command with pipx:

```sh
pipx install scriptvault
```

For local development, run `pipx install --editable .` from the ScriptVault
checkout instead.

## Layout

```text
.sv/vault.toml          scripts, orchestrations and includes
.sv/.env                environment shared by every script
.sv/GUIDE.md            this file
.sv/scripts/NAME        file script, run as `sv NAME`
.sv/scripts/NAME.env    environment for that one script
.sv/local/scripts/NAME gitignored local script, listed by default
.sv/local/scripts/NAME.env environment for that local script
.sv/.gitignore         ignores /local/
.sv/lib/NAME.sh        source-only helper, not a runnable target
```

## Scripts

### File scripts

```sh
#!/bin/sh
# .sv/scripts/hello.sh
echo "hello from $SV_NAME"
```

Run it with `sv hello`. The first line must be `#!` (files without it are
ignored), the name is the file stem and must match `^[a-z0-9][a-z0-9_.-]*$`.
Executable files run directly, everything else runs through `vault.shell`.

### Inline scripts

```toml
[scripts.build]
description = "Compile the project"
cmd = "cc -o app main.c"
```

Arguments arrive as `$1`, `$2`, ... . Inline commands run through
`vault.shell` (default `/bin/sh`, override with
`[vault] shell = "/bin/bash"`).

File-script metadata can omit `cmd`:

```toml
[scripts.hello]
description = "Print a greeting"
```

This requires a same-name script file in `.sv/scripts/`, such as `hello` or
`hello.sh`, with a shebang. Without a matching file, `cmd` is required.

Scripts and orchestrations accept either `desc` or `description`. If both are
set, `description` takes precedence. Descriptions are shown beside names in
`sv list`.

Listings use colors on supported terminals. Piped output, JSON, `TERM=dumb`,
and environments with `NO_COLOR` set remain plain.

On macOS/Linux, captured orchestration and parallel output uses a
pseudo-terminal (PTY) when the output terminal supports color, so child
commands retain their automatic colors. Stdin and signal handling remain
unchanged. Redirected output, `NO_COLOR`, `TERM=dumb`, Windows and unavailable
PTYs use normal pipes instead. Explicit force-color settings in child commands
still apply.

## Running

```sh
sv build                # implied run
sv run build            # explicit
sv run build --release  # arguments go to the script
sv run build -- --flag   # `--` when an argument could look like an sv flag

sv list                 # show visible targets
sv list --all           # include hidden targets
sv guide                # refresh .sv/GUIDE.md when sv is newer than it
sv add deploy           # create .sv/scripts/deploy.sh
sv add personal --local # create .sv/local/scripts/personal.sh
sv edit deploy          # open the script, or its vault.toml entry
sv edit deploy env      # open .sv/scripts/deploy.env
sv edit config          # open vault.toml
sv edit env             # open .sv/.env
sv help
```

## Local And Hidden Scripts

`sv add NAME --local` creates an executable script in `.sv/local/scripts/`
and ensures `.sv/.gitignore` ignores `/local/`. Existing ignore rules are
preserved. Local scripts are listed by default; use `hidden = true` to hide
them. Their adjacent `.env` files are loaded automatically. Local and shared names must not
conflict. Gitignore rules do not untrack files already committed.

Shared helpers can be hidden with metadata:

```toml
[scripts.helper]
hidden = true
cmd = "echo helper"
```

`hidden = true` also works for file-script metadata and orchestrations.
Use `sv list --all` to reveal hidden targets in text, JSON or nested listings.
Hiding is a listing preference, not access control or secret protection.

## Source-Only Helpers

Put reusable shell helpers in `.sv/lib/`, outside the runnable script directory:

```bash
source "$SV_LIB/helper.sh"
source "$SV_TOP_LIB/git-version.sh"
```

`SV_LIB` points to the owning vault's library directory. `SV_TOP_LIB` points
to the outermost vault's library directory in the current execution chain.
If a nested vault is invoked on its own, both point to that nested vault's
library. These paths are injected even when the directories do not yet exist.
Helpers are not runnable targets and never appear in `sv list`, even with
`--all`. Sourcing keeps their functions and variables in the calling shell.

## Orchestrations

A named list of steps that runs in order:

```toml
[orchestrate.ci]
description = "Build, then lint and test together"
steps = [
  { sh = "echo building" },
  { run = "build", args = ["--release"] },
  { parallel = ["lint", "test"] },
]
```

- Each step has exactly one of `run`, `sh` or `parallel`; `args` only works
  with `run`.
- Steps run top to bottom. The first non-zero exit stops the run and becomes
  sv's exit code.
- `parallel` starts every listed target at once; their output is prefixed
  with `[name] `.
- `run` and `parallel` accept scripts as well as other orchestrations,
  resolved in this vault first and then in the included vaults. Prefix a name
  with `include:` (for example `api:build`) to pin it to one include.
  Reference loops are rejected before anything runs.

`sv ci` runs it like any other target, printing progress as it goes:

```text
==> [1/3] echo building
building
==> [2/3] build --release
```

## Included vaults

```toml
[include.api]
path = "services/api"   # a directory containing .sv/vault.toml,
                        # or a direct path to a vault.toml
```

```sh
sv run api build    # run a target of the included vault
sv api build        # same thing
sv run api:build    # the qualified form resolves to the same target
sv api:build        # implied run accepts it too
```

Inside `steps`, included targets are referenced by their plain name or with
the `include:` prefix. Plain names resolve against this vault first, then
against the includes:

```toml
[orchestrate.deploy]
steps = [
  { run = "build" },          # this vault's build, else an include's
  { parallel = ["api:publish", "app:publish"] },  # pinned to one include
]
```

Use `include:target` whenever two includes define the same name; plain names
are ambiguous and the first include wins.

## Environment injection

Environment files are dotenv style: `KEY=VALUE` lines, `#` comments, an
optional `export ` prefix, and quotes around a value are stripped.

Sources are applied in this order, so later ones win:

1. `.sv/.env` - vault-wide defaults
2. `.env` of every included vault (in include order), then `.env` in the
   project root
3. `.sv/scripts/NAME.env`, or `.sv/local/scripts/NAME.env` for local scripts
4. the real environment (your shell)
5. injected `SV_*` variables:
         - `SV_TOP_ROOT` - outermost vault's root directory in the execution chain
     - `SV_TOP_LIB` - that outermost vault's library directory
   - `SV_ROOT` - root directory of the owning vault (the include itself, for
         scripts and orchestrations that come from one)
   - `SV_DIR` - its `.sv` directory
    - `SV_LIB` - its `.sv/lib` directory
   - `SV_CWD` - working directory where sv was invoked
   - `SV_NAME` - name of the script being run

Example:

```dotenv
# .sv/.env
API_URL=https://staging.example

# .sv/scripts/deploy.env
API_URL=https://prod.example
```

`sv run deploy` sees `API_URL=https://prod.example` - unless your shell
already exports `API_URL`, because the real environment wins.

## Interrupting runs

Scripts that run until `^C` (servers, watchers) receive the interrupt
directly: sv shares the terminal's process group and ignores the first `^C`
so the script can shut down, then exits with the script's exit code. A second
`^C` kills every child sv started and exits with code 130.
